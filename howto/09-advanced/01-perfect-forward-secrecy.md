# 9.1 — Perfect Forward Secrecy (Temporary Auth Keys)

[← Previous](../08-sending-a-message/04-reading-updates.md) · [Index](../README.md) · [Next: Connection management →](02-connection-management.md)

---

**You do not need this to log in and send a message.** It is documented for completeness
and because the permanent key alone has a real weakness.

---

## 1. The problem

The permanent `auth_key` never changes. If an attacker records your traffic today and
obtains the key in a year — by seizing the device, or by compelling you — they can decrypt
**everything they recorded**, retroactively.

Diffie-Hellman gives forward secrecy only if the key is discarded. A key stored on disk for
the life of the account is not discarded.

---

## 2. The solution

Use **two** keys:

| Key | Lifetime | Purpose |
|-----|----------|---------|
| Permanent | Forever | Identifies the account; used only to bind temporary keys |
| Temporary | ~24 hours | Encrypts all actual traffic |

The temporary key is generated by the same DH handshake, is **never written to disk**, and
is discarded when it expires. Recorded traffic encrypted with an expired, unstored key
cannot be decrypted later — the key no longer exists anywhere.

TDLib's expiry (`td/telegram/net/Session.cpp:1445`):

```cpp
auto key_validity_time = is_main && !is_cdn_ ? 0 : Random::fast(23 * 60 * 60, 24 * 60 * 60);
```

A random 23-24 hours. Randomizing the lifetime avoids a fleet of clients all re-keying at
the same moment.

---

## 3. Binding

A temporary key on its own is anonymous — the server has no reason to associate it with
your account. **Binding** proves that whoever holds the temporary key also holds the
permanent one.

```
bind_auth_key_inner#75a3f765 nonce:long temp_auth_key_id:long perm_auth_key_id:long
    temp_session_id:long expires_at:int = BindAuthKeyInner;
```
(`td/generate/scheme/mtproto_api.tl:28`)

```
auth.bindTempAuthKey#cdd42a05 perm_auth_key_id:long nonce:long expires_at:int
    encrypted_message:bytes = Bool;
```
(`td/generate/scheme/telegram_api.tl:2323`)

The construction is unusual — a message encrypted with one key, carried inside a message
encrypted with the other.

`SessionConnection::encrypted_bind` (`td/mtproto/SessionConnection.cpp:867-889`):

```cpp
int64 temp_key = auth_data_->get_tmp_auth_key().id();

mtproto_api::bind_auth_key_inner object(nonce, temp_key, perm_key,
                                        auth_data_->get_session_id(), expires_at);
…
MtprotoQuery query{auth_data_->next_message_id(Time::now_cached()), 0,
                   object_packet.as_buffer_slice(), false, {}, false};
PacketStorer<QueryImpl> query_storer(query, Slice());

const AuthKey &main_auth_key = auth_data_->get_main_auth_key();
PacketInfo packet_info;
packet_info.version    = 1;                       // MTProto v1 (SHA-1 KDF)
packet_info.no_crypto_flag = false;
packet_info.salt       = Random::secure_int64();  // random, not the real salt
packet_info.session_id = Random::secure_int64();  // random, not the real session
auto packet = Transport::write(query_storer, main_auth_key, &packet_info);
```

Four details that are easy to miss:

1. **`seq_no = 0`** — the second field of `MtprotoQuery`. Not the session's next sequence
   number.
2. **`version = 1`** — MTProto **v1** with the SHA-1 KDF
   ([4.2](../04-encrypted-messages/02-msg-key-and-kdf.md), `KDF.cpp:17-50`), not v2. This
   is the only place outside secret chats where v1 is used.
3. **Random `salt` and `session_id`** — deliberately *not* the real ones, so the blob
   carries no session-linking information.
4. Encrypted with the **permanent** key, while the outer `auth.bindTempAuthKey` query is
   encrypted with the **temporary** key.

The outer call, from `Session::connection_send_bind_key`
(`td/telegram/net/Session.cpp:1364-1390`):

```cpp
int64 perm_auth_key_id = auth_data_.get_main_auth_key().id();
int64 nonce = Random::secure_int64();
auto expires_at = static_cast<int32>(auth_data_.get_server_time(auth_data_.get_tmp_auth_key().expires_at()));
std::tie(message_id, encrypted) = info->connection_->encrypted_bind(perm_auth_key_id, nonce, expires_at);

NetQueryPtr query = G()->net_query_creator().create(
    last_bind_query_id_, nullptr,
    telegram_api::auth_bindTempAuthKey(perm_auth_key_id, nonce, expires_at, std::move(encrypted)),
    {}, DcId::main(), NetQuery::Type::Common, NetQuery::AuthFlag::On);
```

`nonce` and `expires_at` appear **both** inside the encrypted blob and as plaintext
parameters of the outer call. The server decrypts the blob with the permanent key and
checks that they match — that is the proof.

`auth.bindTempAuthKey` is one of the two calls allowed before authorization completes
(`td/telegram/net/NetQueryCreator.cpp:78-79`).

---

## 4. The full procedure

```
1. Handshake → permanent auth_key.       (persist)
2. Handshake again, with expires_in ≈ 24h → temporary auth_key.  (do NOT persist)
3. Build bind_auth_key_inner(nonce, temp_key_id, perm_key_id, session_id, expires_at).
4. Wrap it as a query with seq_no = 0.
5. Encrypt with the PERMANENT key, MTProto v1, random salt and session_id.
6. Send auth.bindTempAuthKey(perm_key_id, nonce, expires_at, blob),
   encrypted with the TEMPORARY key.
7. On `true`, use the temporary key for everything.
8. When it nears expiry, repeat from 2.
```

### The temp-key handshake

Identical to [chapter 3](../03-auth-key/01-overview.md) with one change: use
`p_q_inner_data_temp_dc#56fddf88` (`mtproto_api.tl:16`) instead of
`p_q_inner_data_dc#a9f55f95` (`:15`). The `_temp_` variant carries an `expires_in:int`
field.

---

## 5. Why you can skip it

| | Permanent only | With PFS |
|-|----------------|----------|
| Login works | ✅ | ✅ |
| Messages work | ✅ | ✅ |
| Traffic encrypted | ✅ | ✅ |
| Retroactive decryption if the key leaks | ❌ vulnerable | ✅ protected |
| Extra handshake per day | — | Yes |
| MTProto **v1** implementation needed | ❌ | ✅ |
| Two auth keys to manage | ❌ | ✅ |

The cost is real: you must implement the SHA-1 KDF purely for the bind blob, and manage two
keys with different lifetimes and storage rules.

> **💡 Recommendation.** Build the permanent-key client first and get it working
> end-to-end. Add PFS afterwards, if the threat model justifies it. Nothing in the login or
> message-sending path changes.

---

## 6. If you do implement it

- [ ] The temporary key is **never** written to disk
- [ ] Its buffer is zeroed on expiry
- [ ] `expires_in` randomized in the 23-24 hour range
- [ ] `bind_auth_key_inner` uses `seq_no = 0`
- [ ] The blob is encrypted with **MTProto v1** (SHA-1 KDF)
- [ ] The blob uses **random** `salt` and `session_id`, not the real ones
- [ ] `nonce` and `expires_at` identical inside the blob and in the outer call
- [ ] The outer `auth.bindTempAuthKey` is encrypted with the **temporary** key
- [ ] Re-keying starts before expiry, not after
- [ ] Failure falls back to the permanent key rather than breaking the client
